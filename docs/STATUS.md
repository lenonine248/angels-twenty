### 指示を出すときの決まり `[必読]`

**UI から機体に指示を出すときは `Aircraft.setPlayerOrder()` を使う。**
`setOrder()` を直接呼んではいけない。

`player: true` が付いていない指示は `PilotAI._playerLocked` を通らないので、
**次の tick で AI に上書きされる**。付け忘れは3回踏んでいる。

| いつ | どこ | 症状 |
|---|---|---|
| Beta 2.22 | 編隊の追従指示 | 1機ずつなら効くのに編隊だと効かない |
| Beta 2.32 | B キーの帰投（`commands.orderRtb`） | 対地攻撃モードだけ帰投できない（パネルのボタンは効く） |

どちらも「指示は入っているのに次の瞬間に消える」という同じ形で出るので、
**指示の直後を見ても分からない**。数秒進めてから `u.order.type` を見ること。
Beta 2.32 で経路を1本にまとめ、`player: true` を手で書く場所は
`setPlayerOrder` の中だけになった。

### ベンチの数字の読み方 `[必読]`

**司令官AIで 6〜7割クリアが適正**（§41・プレイヤーが決めた基準）。
**9〜10割は「簡単寄り」。合計クリア数を最大化する読み方はしない。**

人が指揮すれば司令官AIより良い結果になるし、運の比重もあるので
「安定してクリアできる」状態は難易度として緩い、というのが理由。

| 司令官AIの成績 | 読み方 |
|---|---|
| 9〜10割 | 簡単寄り |
| **6〜7割** | **適正** |
| 3〜5割 | 難しめ |
| 0〜2割 | 壊れている疑い |

**何を積んで測るのかも決まっている**（§41.2）。

| | 決め |
|---|---|
| **プリセットの搭載** | 兵装コストが **○評価の帯**に入るように組む。ただし**帯のほうを搭載に合わせる**（§45.1） |
| **プリセットの兵装** | **AAM-S と AAM-M だけ。** AAM-A は2スロット食って旋回率まで動くので、釣り合いの調整に使わない（§45.2） |
| **`weaponPoints` の上限** | **全ハードポイントを AAM-M で埋めても収まる高さ**（§48.2）。点を気にしなければ厚く積んでクリアできる余地を残す。**COASTAL WALL だけは例外**（§90 で 40P ＝ 埋めると 42P 要るので届かない。対地の面なので空対空で埋め切る積み方を想定せず、**積み直し1回ぶん**で上限を決めた・プレイヤーの決め） |
| **S ランク** | やりこみ。**難易度の設計基準にしない** |

> **点を埋めるために兵装を厚くすると螺旋になる**（§45.1）。
> 搭載を厚くする → 成績が上がる → 敵を増やして戻す、で
> 序盤のミッションが初心者向けでなくなった。**帯は調整できる値。**

**後半4ステージだけは例外**（§41.3）。**対地が絡むと司令官AIが適切に対処できない**
（特に SAM は対処を誤ると一方的に撃破される）。
**0/12 は「ステージが壊れている」ではなく「ベンチが測れていない」。**
判定は**テストプレイ**で行う。ベンチは「同じ種で前後を比べて変わったかどうか」
を見るぶんには有効。

> **距離は難易度の軸として当てにならない**（§41.4）。
> 初陣は +3km で 61%、+4.5km で 100% と**崖**があり、
> 緊発は遠ざけても近づけても 100% に戻ってしまった。効いたのは**機数**。
>
> **位置を動かす掃引では対地高度を保ち直すこと。** `pos.x/z` だけ動かして
> `pos.y` を放置すると、ステージ定義側（移動先の地形高度＋agl）と別条件になる。
> **12シードでは足りない**（標準誤差 ±14ポイント）。帯を狙うなら18シード。

**緊急発進は、物理の改善を5回連続で止めてきたミッション**（§36.1）。
それが**迎撃機がまともな距離で撃てるようになった途端に成立した**のは大きい。

### 調整の教訓（同じ失敗を繰り返さないために）

実測して初めて分かったこと。どれも直感と逆だった。

- **「撃つ判断のしきい値」は難易度の軸にならない**。ミサイルが実体で飛ぶため、
  しきい値を下げれば手数が増えて強くなり、上げれば良い射点でだけ撃つので強くなる。
  **どちらへ動かしても強くなる**（両方向とも実測で確認）
- **時間制限のある防衛任務では、敵の練度を下げると難しくなる**。
  敵が消極的になって戦闘が長引き、その間に爆撃機が目標へ到達する。
  ミッション1で練度0.8にしたら 6/6 → 0/6 になった
- **迎撃させたい敵を遠くに置くと、かえって守りにくくなる**。
  迎撃が遠方になり、護衛と戦っている間に本命だけが抜けてくる
- **回避の降下は浅くしてはいけない**。「高度＝エネルギー」と考えて浅くしたら、
  生存率がはっきり落ちた。深く降ろすのが正しい（段差を作らないことだけが要点）
- **1回の攻撃で決着するステージは結果が極端に振れる**。
  間に合うか否かの紙一重になり、わずかな初期差で 6/6 と 0/6 が入れ替わる

### これからの方針（2026-08-21 に合意）

**挙動はシミュレーター寄り、操縦はAI、プレイヤーは指示だけ。**
機体とミサイルは実機に近い理屈で動かし、それを直接操るのはAIに任せる。
難易度を抑えたまま戦闘のリアリティを出し、プレイヤーは指揮に集中する。

### 敵の練度（skill）

難易度を「敵の数」ではなく「腕」で調整するダイヤル。ステージ定義に `enemy.skill`（0.2〜1、既定1）。

効く先: 判断間隔 / 発射間隔 / 照準精度 / 機銃命中率 / 回避の質 / デコイを撒く早さ。

**撃つ判断のしきい値には効かせていない。** ミサイルが実体で飛ぶため、
しきい値を下げれば手数が増えて強くなり、上げれば良い射点でだけ撃つので強くなる。
どちらへ動かしても強くなるので難易度の軸にならない（実測で両方向とも強くなった）。

> **`[実測・§70.12］` 練度は釣り合いのダイヤルとして使えない。**
> 上限が 1.0 なので上へ回せず、**1.0 → 0.8 へ下げても誤差の範囲**でしか動かない。
> **効くダイヤルは機数** —— 初陣を3機にしたときは +39pt 効いた（§70.13）。
> 第5段で釣り合いを取るときは、練度ではなく機数と位置で組むこと。

**`[計算・未実測・2026-09-26]` 上限 1 を外したときの伸び**（`Aircraft` の `clamp(o.skill, 0.2, 1)` を外した場合。式から計算しただけ）

| 効き先 | 式 | 1.0 | 1.2 | 1.5 | 2.0 |
|---|---|---|---|---|---|
| 判断間隔（`pilot.js` の `AI_INTERVAL`） | 0.5 ÷ (0.6+0.4k) 秒 | 0.50 | 0.46 | 0.42 | 0.36 |
| ミサイル・爆弾の次弾間隔（`FIRE_COOLDOWN`） | 3.5 ÷ (0.5+0.5k) 秒 | 3.50 | 3.18 | 2.80 | 2.33 |
| 機銃の散布（`gunSpread`） | ÷ (0.6+0.4k) | 1.00 | 0.93 | 0.83 | 0.71 |
| ブレイク距離（`acm.js` の `BREAK_RANGE`） | 1200 × (0.35+0.65k) m | 1200 | 1356 | 1590 | 1980 |
| ミサイルの照準ずれ | k<1 のときだけ | 0 | 0 | 0 | 0 |
| デコイを撒き始める時刻（`_decoyStartTti`） | 式の中で 0〜1 に切る | 11秒前 | 11 | 11 | 11 |

- **飛行性能と兵装の威力・射程には効かない。** 1 を超えて伸びるのは判断・手数・機銃の集弾の3つだけ
- **ブレイク距離は 1 を超えると伸びすぎる。** 1.5 の 1,590m は、`acm.js` のコメントが「1,600m まで広げると撃たれてもいないのに延々と回避する」と書いている距離（コメントの記録・未測定）。上限を外すならブレイクは 1 で止める
- **調整パネル（§47）は 1.4 まで入るが、本体が 1 で切るので、いまは 1 を超える値は何もしない**
- 練度が入るのは**敵だけ**（自軍機は常に 1）

### シミュレーションの決定論 `[必読]`

同じステージ・同じシードから始めれば**毎回まったく同じ経過になる**。

実測: ミッション1を4回、90秒ぶん進めて全ユニットの座標とHPを比較 →
**小数3桁まで完全一致**。

そうなっていなかった原因は `sim/unit.js` / `sim/missile.js` / `ai/formation.js` の
`nextId` が戦闘をまたいで増え続けていたこと。ID はレーダーの扇の分担と
逆探知の位置誤差に効くので、**その回までに何戦したかで経過が変わっていた**
（`tools/bench.js` の注意書きはこれ）。戦闘を組むたびにリセットするようにした。

乱数の側は元から揃っていた。`Math.random()` は `core/audio.js` と
`world/effects.js`（どちらも演出）にしか無く、`sim/` は全て `world.rng`
（`stage.terrain.seed` から作るシード付き mulberry32）を通る。
`performance.now()` はループの計時・探知の統計・モデルの揺れだけで判断に入らない。

**ベンチを回すときの注意**: `AT.startStage()` は戦闘を組むまでに2フレーム挟むので、
`setSpeed(0)` が効くまでに実ループが 2〜3 ステップ進む。この**進んだ数が揃わないと
結果も揃わない**（実測で 2 ステップの回どうしは一致、3 ステップの回だけ違った）。
手で回して比べるときは、進んだ分を数えてから残りを足すこと。

### 兵装を積むことの代償 — `js/sim/aircraft.js`

**2つだけ。** どちらも `搭載スロット ÷ ハードポイント数` に比例する。

| | 満載時 | 場所 |
|---|---|---|
| **旋回率** | **−25%** | `effectiveTurnRate` の `loadFactor` |
| **燃料消費** | **+30%** | `_consumeFuel` |

速度・加速度・上昇率には影響しない。
**増槽(TANK)を持ち帰るとこの代償だけが残る**（燃料はもう入っていない）ので、
投棄の仕組み（§32 で実装済み）に意味が出る。

## 5. 残課題

### 既知の簡略化・割り切り

- **整備が終わった機体は自動では再発進しない**。プレイヤーが発進を指示する（仕様通り）
- **移動する既知目標のブリーフィング情報は見失う**。艦船などに `known:true` を付けても、
  記憶は不確かさで切れる（§54）。**静止目標だけが恒久的に記憶される**
- **編隊はAIの連携（扇の分担・目標の重複回避）が主。隊形の維持は随伴指示に依存**
- **ARM は沈黙された相手を確実には殺せない**（21kmから2発で79%）。これは意図した駆け引き
- **BGM は「戦闘機の機内」の環境音に寄せてある**。曲として聴かせる作りではない
- **AI は雲を理解しない**（§88.17。測ったうえで作らないと決めた）

### 手が付いていないもの

- **目視内でチャフを温存する**（§34.5 の残り）。いまは距離に関係なく撒く。
  **これも §38 で意味が出た** — 目視外で撒く先ができたので、残す価値がある

- **輸送機に独立した型を与える**（§39.2）。ESCORT の「CARGO」は
  **早期警戒機 E-8 の型を流用している**。そのため「AWACS を落としやすくする」
  変更が、そのまま**味方の輸送機を弱くする**という形で効いてしまう
  （§39 の AB 廃止で ESCORT が 15/18 → 14/18）。
  型を分ければ両者を別々に調整できる
- **§28.7 の残り1段階**（ロック中の索敵縮小）。
  AAM-M が弱くなりすぎるので止めてあった（§28.11）。
  **ロック警報は Beta 2.30 で入れた**（§37.2）— 3ステージで結果は1ビットも変わらなかった

- **§22.4.3 編隊の戦術連携の残り。** 囮と仕留め役、2機1組を2つという単位。
  **挟撃（§22.4.2）と役割の分担（§22.4.4）は測って入れなかった。**
  どちらも「3対3で15秒で決着する交戦には編隊戦術が効く余地がない」という同じ壁。
  **再挑戦は交戦の規模を大きくしてから**（§30.5）— 目標の候補が機数より多い／
  自由機が存在する／交戦がミサイルの飛翔時間より長く続く、の3つが要る
- **§22.3.7 空戦機動の残り。** ローリング・シザース、練度と機動の結び付け。
  **正面での会敵の判断は測って見送った**（§22.3.6.1）—
  アスペクトで命中率がほとんど変わらない（正面47% / 側方43% / 後方44%）。
  練度との結び付けは、**8ステージすべて `skill` が 1.0 なので効く先が無い**
- **評価基準の見直し。** 基準値は ESCORT を除いて机上の見積りのまま。
  ただし**各ステージのコメントに根拠が書いてある**ので、読まずに引き直さないこと
  （§32.6 で一括に引き直して戻した）。
  `python tools/playlog.py` の「評価」列で S/A/B/C の分布を見て詰める

- **AWACS の逃げ方**（`EVADE` の作り直し）。いまは「26km以内の敵から離れる」だけで
  **帰る場所の概念が無い**ため、地図を広げても端へ逃げるだけになる。
  敵から離れるのではなく**自陣側へ後退**させたい
- **SCRAMBLE の作り直し**（地上発進・敵は未探知・距離を取る）は保留のまま
- **`RUN_TTI` を測り直す**（§37.3）。いま 20 のまま未検証

### 将来拡張（優先度低・未着手）

- **キャンペーン（機体持ち越し）** — タイトル画面に「準備中」として出ている、
  **唯一の未達の約束**。撃墜が次ステージに響く。データ構造は後付け可能にしてある。
  補充・修理・詰み防止（ミッション単位の再挑戦）を先に決めること。**Beta 3 の中身**
- **地図を広げる**（`MAP_SIZE` 51.2km → 80km 程度）＋**新しいステージ**（§30.5）。
  広げるだけでは既存ステージが隅に固まるだけで進出距離は伸びない。
  そこで戦うために作られたステージと一緒に入れること
- **敵のエース機**（2026-09-26・アイデア段階・実装はまだしない）—— 機体ごとに練度を割り振って、
  敵にエースを出したい（プレイヤーの案）。**作る前に仕様を詰める**
  - **データはもう半分ある**: 最初からいる敵は `a.skill ?? stage.enemy?.skill ?? 1`（`main.js` の敵の生成）で
    機体ごとに読む。足りないのは、エディタの欄（面全体の「敵の練度」しかない）・増援（面の既定しか渡さない）・上限 1
  - **練度だけでは伸びしろが小さい**: 本編の敵は既定の 1＝満点なので、エースが上に行く余地が無い。
    上限を外しても 1.5 で判断2割・手数25%ほど（§3「敵の練度」の表）。並の敵を下げてエースを 1 にすると、
    全面の釣り合いが動く（ベンチ取り直し）
  - **見て分かる区分にする**: 機体ごとに自由な数字を振れると、同じ見た目の機体が面ごとに違う強さになり、
    「面ごとに能力値を変えない」決めとぶつかる。**エースは決まった1区分**（印＝コールサイン・色・無線など／
    中身は全面で共通）にすれば、「エースは〇〇してくる」が知識として別の面へ持ち越せる
  - 強さは練度の数字より**振る舞いの違い**（デコイの撒き方・撃つ位置の選び方・僚機との連携など）で作るほうが
    向くかもしれない（どれが効くかは未測定）
  - **仕様で決めること**: 強さを何で作るか（練度の上限／振る舞い／両方）・プレイヤーへの見せ方・
    1種類か段階か・増援にも出すか・評価と絡めるか（エースを落とすと何かあるか）
- パイロット育成、夜間ミッション

> ステージエディタ（§66）と天候・雲（§88）はここにあったが、**どちらも実装済み**。

### LONG WATCH の過程 — `tools/watchprobe.js`

```js
await fetch('/tools/bench.js').then(r => r.text()).then(eval)
await fetch('/tools/watchprobe.js').then(r => r.text()).then(eval)
await AT.watch.run('現行', AT.watch.SEEDS11)               // 1変種を18種
await AT.watch.compare(undefined, AT.watch.SEEDS11)        // 4変種を同じ種で並べる
```

**クリア数が何も言わない面のために作った**（§92.4）。`mission.update` を包んで毎刻み覗くだけで
**判定は変えない**。出すもの: 施設の残りと落ちた時刻・空にいる敵機の数（t150/300/390/480/600/750）・
増援が湧いた数・撃墜の中身（B-9 / J-7 / GUARD）・損失の中身（機体 / 施設 / 防空）・
**攻めの側**（飛行場を攻撃目標にした時刻・最接近・削った hp）・**自軍機が落ちた場所と任務**。
各戦の行は `AT.watch.last[変種]` に残る。

変種は `現行` / `GUARD抜き` / `旧間隔`（`every: 150`）/ `旧間隔GUARD抜き`（＝公開版 Beta 2.95 の面）。
**GUARD抜き系は原因を割るための形で、出荷する形ではない。**
`旧間隔GUARD抜き` は `SEEDS11` で **4/18**（Beta 2.95 と一致）に戻る —— ハーネスの健全性の基準。
ただし**乱数列までは揃わない**（配置の `jit` が機体ごとに `world.rng()` を引くので、
GUARD を湧かせてから消すと以降の引きがずれる。損失は 3.8 → 3.94）。

**「空にいる敵機」は t600 以降、生き残った戦だけの値**で、着陸して積み直している機は数えない。
窓の大きさとしては読まないこと。

### AAM-M が撃てない理由 — `tools/aammprobe.js`

```js
await fetch('/tools/bench.js').then(r => r.text()).then(eval)
await fetch('/tools/aammprobe.js').then(r => r.text()).then(eval)
await AT.aamm.run(6, 6, [11, 22, 33, 44, 55, 66])   // 面6＝LONG WATCH
await AT.aamm.fan(6, [11, 22, 33, 44, 55, 66])      // 縦の扇 20/30/40 のA/B
```

`inEnvelope` を横から数えるだけで**判定は変えない**。落ちた理由を `_envelopeReason`
の言葉で分類し、**縦の扇で落ちたぶんが「水平線から測れば扇の内側」だったか**を出す
（§92.3）。**`report()` の判定は `FOV = 20` 固定**なので、`fan()` で扇を広げた周回と
突き合わせるときはそこを読み替えること。

**幾何の規則を触ったときは結末ではなく「その規則が働いた回数と、働いた瞬間の値」を
測る**（§82.3 の教訓）—— この道具はそのために作った。

`AT.aamm.compare(面, 種)` は対策の変種を同じ種で並べる（既定は `AT.aamm.SEEDS18` の18種）。
**割合と件数の両方を出す** —— §92.3 では割合だけを見て、
**分母が膨らんでいるのを効果と読み違えた。**

差し替えは **`Aircraft.prototype` と `ALL_TYPES`（`spec` は機種で共有）に掛けて必ず戻す**。
**機体ごとに掛けると湧いてくる増援に漏れる** —— LONG WATCH は敵機の半分が増援なので、
「対策なし」の周回で増援だけ対策が効いている状態を測ることになる。
`AIRCRAFT_TYPES` / `ENEMY_TYPES` を渡せば**陣営ごとに**掛けられる
（出荷する形ではなく、代償がどちら側から出ているかを割るため）。

### ミサイルの素の性能 — `tools/kinematics.js`

```js
await fetch('/tools/bench.js').then(r => r.text()).then(eval)
await fetch('/tools/kinematics.js').then(r => r.text()).then(eval)
await AT.kin.run({ ranges: [2,4,8,12,16,20], aspects: [0,90,180] })
AT.kin.report()
await AT.kin.threshold({ weapon: 'AAM-M', key: 'turnRate' })

// 対抗手段を入れたまま、その距離から撃って何割当たるかを測る（§37.5）
await AT.kin.run({ live: true, weapons: ['AAM-M'], ranges: [4,8,12,16,18,20],
                   seeds: [11,22,33,44,55,66,77,88] })
```

> **`live` は較正のための道具。** ベンチの命中率は
> 「AI がその距離で撃つかどうか」に汚染されていて、較正には使えない
> — 実際 8km より遠くの発射が1件も無いので、そこの命中率は測れない（§37.5）。
> `live` なら距離を指定して撃たせられる。

**対抗手段をすべて外して、回避軌道だけで振り切れるかを測る**（§33）。
デコイ・ノッチ・クラッター・照射切れ・シーカーの捕捉を一括で無効にし、
残すのは速度・旋回率・エネルギー・警報の遅れだけ。

> **命中率の議論が対抗手段の話に流れるのを防ぐための道具。**
> 「チャフが強い／弱い」を動かす前に、
> **チャフが1枚も無いときにその距離で当たってよいのか**を先に決める。

結末は 撃墜 / 至近弾 / 回避 の3つに分ける。
**至近弾（当たったが落ちない）を「外れ」と混ぜない** — 混ぜると原因を取り違える。

### 命中期待度の較正 — `tools/calib.js`

```js
await fetch('/tools/calib.js').then(r => r.text()).then(eval)
await AT.calib.run([0, 1, 5], [11, 22, 33, 44, 55, 66])
AT.calib.report()
```

**発射ごとに「そのとき予測した期待度」と「実際どうなったか」を対で残す。**
結末を 命中 / デコイ / 誘導喪失 / 外れ に分け、距離帯・兵装別・表示ラベル別に出す。

誘導喪失には**理由**が入る（`AT.calib.rows` の `理由` 列）。
照射切れ / 終末で捕捉できず / ノッチ / クラッター / 地形遮蔽 / 目標消失 / 発射機喪失。
`Missile._goStupid(reason)` が付ける。**§28.13 はこれが無ければ解けなかった**
— 「デコイが強い」に見えていた不具合が、実は AAM-A のシーカーと
AAM-M の照射切れだったことが、理由を割って初めて見えた。

> **兵装ごとに結末を分けるのが肝。** ミッション1が壊れたとき、
> 全体の命中率を見ているうちは原因が分からなかった。
> 兵装別に割ったら **AAM-M だけが 30発撃って命中ゼロ**と一目で出た（§28.12）。

> **版どうしの比較にこの数字を使ってはいけない。**
> Beta 2.9 で種を毎回引くようにしたので、**同じ版でも回ごとに大きく振れる**。
> ミッション1は種によって「3撃墜クリア」から「0撃墜で全滅」まで動く。
>
> 比較するときは**種を固定して A/B する**。同じプロセスの中で条件だけ
> 差し替えられるなら `AT.bench.ab()` が速い。
>
> ```js
> await AT.bench.ab(0, [11, 22, 33, 44, 55, 66], {
>   敵ON:   (b) => { for (const u of b.world.units)
>            if (u.side === 'red' && u.kind === 'aircraft') u.radarMode = 'on'; },
>   敵自動: (b) => { for (const u of b.world.units)
>            if (u.side === 'red' && u.kind === 'aircraft') u.radarMode = 'auto'; },
> })
> ```
>
> 種ごとに `state / 撃墜 / 損失 / 秒` の指紋を突き合わせ、**違った種だけ ★** が付く。
> ★ が1つも付かなければ、その変更はその条件では何も動かしていない。
> 第2引数の関数は**戦闘が組み上がった直後・1ステップも進める前**に呼ばれる。
> 進めた後に触っても A/B にならない。
>
> 増援が絡むステージ（DAWN BLADE・TOTAL WAR）では、`world.spawnReinforcement` を
> 包んで**後から湧く機体にも同じ条件を掛ける**こと。忘れると条件が混ざる。
>
> コードそのものを入れ替える必要がある変更（定数や式の書き換え）は、
> 同じプロセスで切り替えられないので `git stash` / `git stash pop` を挟み、
> **同じ種の配列**で両方を回して 1 対 1 で比べる。
>
> この方法で Beta 2.9（逆探知）と Beta 2.11（電波管制）の効きを切り分け、
> Beta 2.12 で §26.6 が現行の地図では測れないことを確かめた。
> ランダムな種のままでは、どれも「悪化した」ようにしか見えなかった。

### 音が鳴っているかを確かめる

耳で確認できない場合は、アナライザを繋いで RMS を測る。

```js
const an = AT.audio.ctx.createAnalyser(); an.fftSize = 2048;
AT.audio.master.connect(an);
const buf = new Float32Array(2048);
setInterval(() => { an.getFloatTimeDomainData(buf);
  let s = 0; for (const v of buf) s += v * v;
  console.log(Math.sqrt(s / 2048).toFixed(3)); }, 500);
```

BGMのみで 0.08 前後、戦闘中で 0.13 前後、爆発の瞬間に 0.27 まで上がる。

### 開発時に踏んだ罠（同じところで詰まらないために）

- **描画が止まっている環境では計測できない**。バックグラウンドタブや
  ブラウザペインが非表示だと `requestAnimationFrame` が止まり、
  `syncGroundView` などの描画側の同期も走らない。
  表示に関わる検証をするときは、同期関数を明示的に呼んでから測ること
  （飛行場の向きの検証で、これを忘れて誤った「ずれ67.5度」を出した）
- **同じ理由でシミュレーションも進まない**。`document.visibilityState` が
  `'hidden'` のあいだ `fixedUpdate` が一度も呼ばれないため、
  「戦闘を始めて目標達成にして戦果画面を見る」形の検証は成立しない。
  測る前に `AT.loop.simTime` が実際に増えているかを確かめること。
  ペインを表示できないときは `tools/bench.js` のように手で回すか、
  画面側の関数（`screens.showResult` など）を直接呼んで確かめる
- **ベンチを2つ同時に走らせない**。ツールのタイムアウトで手元に結果が返らなくても
  裏では走り続けており、次の計測と混ざる
- **手動ステップの検証では機体が生きているか確認する**（`u.alive` / `u.deathCause`）。
  前のテストで死んだ機体を測っていたことが何度もある
- **地上待機のステージ（3以降）では、機体を発進させないと AI が一切動かない**。
  `_think` が `u.onGround` で弾くため、指示を出しても何も起きない
- **戦闘を組み直したあと `AT.battle` が真になるのを待っても意味がない**。
  `startBattle` は nextFrame を挟むので、しばらく**前の戦闘のまま**。
  待つなら「前と違うオブジェクトになったか」を見る（ベンチと同じ罠）
- **ペイン非表示だと rAF が絞られ、倍速を上げても実測が進まない**。
  チュートリアルの検証では、`fixedUpdate` 相当を手で回す関数を用意して
  `AT.tutorial.update()` も自分で呼ぶのが早い（`tools/bench.js` と同じ考え方）

### 注意

- バックグラウンドタブでは `requestAnimationFrame` が止まるため描画ループは進まない
- 手動ステップでの検証時は、機体が前のテストで死んでいないか
  （`u.alive` / `u.deathCause`）を必ず確認すること。過去に何度かこれで誤った計測をしている
- **ユニットIDは戦闘ごとに1から振り直される**（`resetUnitIds()`・`js/main.js:525`）。
  レーダーの扇の分担や逆探知の位置誤差が ID から決まるため、
  **同じ種・同じステージなら経過はまったく同じになる**（§24）。
  種を変えれば散るので、釣り合いを見るときは18種まわして分布で読む（§41）
